# Kanna secure channel (mobile ↔ desktop end-to-end encryption)

Status: implemented for mobile↔desktop sessions and control over LAN and
relay (Slices 0–2 of task `f4493c65`, 2026-09-16). The Firestore task index
(Slice 3), push bodies (Slice 4) and desktop↔desktop traffic (Slice 5) are
**not** covered by this document and remain as described in §6.

## 1. What it is

Every Kanna Stream Protocol (KSP) session between a paired phone and a
desktop is wrapped in a *Kanna secure channel* (KSC): a Noise Protocol
Framework `IK` handshake (`Noise_IK_25519_ChaChaPoly_SHA256`) followed by
Noise transport messages. The phone's REST-shaped calls ride inside the
same session as KSP `request`/`response` frames, so over the relay the only
thing the relay ever carries for a paired phone is ciphertext.

Implementations:

- Rust: `crates/kanna-secure-channel` over the `snow` crate (RustCrypto/dalek
  resolver, already vendored in this workspace). Used by `kanna-server`.
- TypeScript: `packages/secure-channel`, a spec-exact transcription of the
  IK pattern over `@noble/curves`, `@noble/ciphers` and `@noble/hashes`
  (pure JS, Hermes-compatible). Used by the mobile app and by tests.

Both are gated by `tests/secure-channel-vectors/`:

- `noise-ik-25519-chachapoly-sha256.json` — the published cacophony vector for
  exactly this pattern/cipher/hash, run through `snow` and through the TS
  core.
- `ksc-cross-language.json` — generated by the Rust crate with fixed keys
  (`KSC_WRITE_VECTORS=1 cargo test -p kanna-secure-channel --test vectors`);
  the TS package must reproduce every wire frame as initiator *and* as
  responder, and the Rust test asserts the committed file is still what the
  crate produces.

Nothing about keys, nonces or transcripts is home-made. What this repo
defines is *only*: the prologue, the two hello payloads, the framing, the
close semantics and the authority model below.

## 2. Wire format

- **Prologue**: `kanna-ksc/1` `\0` `<desktop_id>`. Binds the protocol
  version and the target desktop into the transcript; a mismatch fails the
  handshake.
- **Message 1** (phone → desktop): Noise IK message 1. Its encrypted payload
  is JSON `InitiatorHello { version: 1, intent: "session" | "pairing",
  deviceId?, capabilities? }`. The phone's static key is inside the
  encrypted part, so a LAN sniffer learns no device identity.
- **Message 2** (desktop → phone): Noise IK message 2, encrypted payload JSON
  `ResponderHello { version: 1, desktopId, capabilities? }`. The phone
  refuses a `desktopId` other than the one it dialled.
- **Transport**: each Noise transport message's plaintext is one *kind* byte
  followed by a chunk: `1` data with more to follow, `2` final data chunk,
  `3` authenticated close (payload: UTF-8 reason, ≤ 1024 bytes). Per-direction
  nonces are implicit and strictly sequential. A replayed, reordered,
  tampered or truncated message fails authentication and **ends the session**
  on the receiving side; nothing after a failure is delivered.
- **Wire text**: one WebSocket text frame = `ksc1:` + standard base64 of one
  or more length-prefixed (`u16` big-endian) Noise messages. One logical KSP
  frame is sent as one wire frame (chunked into as many ≤ 65535-byte Noise
  messages as it needs); reassembly is bounded at 128 MiB. Text framing is
  deliberate: it is the one form every hop (relay, React Native, Node,
  tungstenite) treats identically, at ~33 % size overhead over binary.

There is no rekey; sessions are bounded by reconnect, and every reconnect is
a fresh handshake with fresh ephemerals (forward secrecy in both directions
against later compromise of either static key).

The **short authentication string** is six decimal digits:
`SHA-256("kanna-ksc/sas/1\0" || handshake_hash)[0..4] mod 10^6`. Both peers
derive it from their own transcript.

## 3. Identities and where they live

| Party | Key | Storage |
|---|---|---|
| Desktop | X25519 *channel identity* | `secure-channel-identity.json` beside the pairing store, `0600`, via `secure_file::atomic_write_0600`; generated from the OS CSPRNG; **fails closed** on a corrupt/loose-permission file (no sealed sessions, no `channelPublicKey` on status) rather than regenerating a key phones have pinned |
| Phone | X25519 *device identity* | `expo-secure-store`, `WHEN_UNLOCKED_THIS_DEVICE_ONLY` (Keychain / Keystore-backed), one per install; a corrupt value is replaced and the phone re-pairs |
| Phone, per desktop | the desktop's public key | `TrustedDesktopRecord.channelPublicKey` in AsyncStorage (a public value; its integrity is protected by the same app sandbox as everything else the app trusts) |
| Desktop, per device | the phone's public key | `TrustedDevice.channel_public_key` in the pairing store |

Randomness on the phone comes only from `expo-crypto`'s CSPRNG (or WebCrypto
in Node); there is no `Math.random` fallback anywhere on the identity, task-id
or handshake paths — a runtime without secure randomness fails loudly.

The desktop's channel identity is distinct from its Ed25519 push identity,
its LAN TLS CA and its task-transfer X25519 key: a key used in one protocol
is never reused in another.

## 4. Pairing: how the desktop key is anchored

Trust is anchored in the pairing ceremony, never in the relay, Firestore or
Bonjour.

**QR path** (recommended; works over LAN or relay). The pairing QR is
`KANNA2:<DESKTOP-ID>:<CODE>:<base32 channel key>:<base32 QR secret>`. The
phone pins the desktop key it *scanned*, opens a sealed session against it
(LAN `ws://` if the desktop is advertised, otherwise a relay tunnel), and
sends the claim `{ code, deviceId, deviceName, qrSecret }` as a sealed
request. The desktop verifies the code (5 attempts, 5-minute TTL, as before)
and the QR secret — which only ever existed on the desktop's screen and
inside the sealed request — and registers the phone's *handshake* static key.
No comparison by a person is needed: the key came from the screen.

**Typed-code path** (LAN only). The phone reads `channelPublicKey` from the
desktop's plaintext `/v1/status` (trust on first use), opens a sealed session
against it and claims with the code alone. The desktop consumes the code and
parks a *pending confirmation* keyed by the session's handshake hash. Both
screens show their own SAS; the person confirms on the desktop only if they
match. Confirmation persists the phone's handshake key; rejection, expiry
(3 minutes) or the sealed session going away persists nothing. Over the
relay a typed code is refused: a typed code pins nothing, and the SAS
comparison assumes both screens are in the room.

The desktop's confirm and reject calls name the claim that was on screen
(`handshakeHash` and `deviceId`, echoed from
`GET /v1/pairing/pending-confirmation`). At most one claim is undecided at a
time, and a new claim replaces the undecided one, so a click meant for a
render that has since been replaced answers `409` and confirms nothing: the
person can never authorize a peer other than the one whose code they
compared. A decision already given is persisted at once and kept (up to
60 s past its window) until the phone that claimed collects it, so a later
claim cannot erase it.

A wrong QR secret with the right code counts as a failed attempt. A
key-bearing QR whose desktop advertises a different key on `/v1/status` is
refused without opening a socket. A typed-code claim that a desktop accepts
*without* parking a confirmation (an immediate `200`) is refused by the
phone and persists nothing: the confirmation step is the only thing that
authenticates a key the phone took from the network.

**Limitation of the typed-code path.** The phone cannot verify that a
person actually confirmed anything on the real desktop; it only observes
that *some* responder parked a confirmation and later answered it. A
network impostor that advertises its own key on `/v1/status`, parks a
confirmation of its own and answers the poll, without ever involving the
real desktop, is not detected by the phone alone: the detection is the
person noticing that the real desktop shows no matching code (or none at
all) and rejecting or ignoring it, and the impostor learns only the
six-character pairing code, which it cannot use against the real desktop
because the sealed claim to the real desktop is what consumes it. The QR
path is the recommended anchor because the key comes from the desktop's
screen and the QR-only secret proves that to the desktop.

The claim response's `deviceSecret` is still issued (legacy compatibility
while old paths are on) but a sealed client never sends it.

## 5. Authority model on the desktop

Decided once per session, at the handshake, in `ksp::admit_sealed_session`:

- Phone static key matches a `TrustedDevice` → **device authority**. Requests
  dispatch with `TrustedLanDeviceAccess` — exactly the LAN-paired route set
  (task control, files, diffs) over LAN *and* relay — and never
  `AuthenticatedHttpInvoke`, the relay's account-level marker, which grants
  more. `DesktopLocalAccess` routes (pairing controls, settings) stay refused.
- Unknown static key → **pairing-only authority**. The KSP layer admits only
  `auth` and `request` frames, and the dispatch layer routes only
  `POST /v1/pairing/sessions/claim` and `GET /v1/pairing/confirmation`,
  inserting no task authority at all. Anything else ends the connection, and
  the session is never subscribed to the task-state broadcast, so it sees
  no task id, activity, read state or output preview it did not ask for.
- A `deviceId` in the hello that names a different paired device than the
  key does is refused.

**Relay account access inside a tunnel.** The relay admits a tunnel but
cannot read what rides in it, so the desktop enforces the account access
the relay last reported (`RelayAccess`): `Enforced(entitlement)` from an
enforcing relay's `auth_ok`, `Unenforced` when the relay authenticated
without an entitlement snapshot (it does not enforce one), and `Unknown`
before the first authentication, after sign-out or after the account
changed. A session that arrived through a relay tunnel — sealed or legacy
plaintext — is served only while that access allows it: `Enforced` with
`active: false` and `Unknown` both refuse, and the refusal covers every
frame that reaches a task, not only `request` (`402 subscription_required`
on a request, an `error` frame with code `subscription_required` on attach
and input). LAN sessions have no relay in the path and are not gated.

Revocation: `remove_trusted_device` persists the removal, then broadcasts
the device id. Admission subscribes to that broadcast *before* it reads the
pairing store and re-reads the store after the handshake, so a removal
that lands at any point — before the lookup, between the lookup and the
session loop, or during the session — is seen: every live sealed session
for that device closes with an authenticated `device revoked` close, a
session admitted across the removal starts pairing-only, and the next
handshake with that key is pairing-only. A rotated desktop key fails every
phone's handshake (`identity_mismatch` → "Desktop identity changed — remove
and pair again").

Task inputs delivered over a sealed session are recorded exactly as
LAN-paired inputs are today.

## 6. What is and is not protected (honest statement)

After this work, for a phone paired with a `KANNA2` QR or a confirmed typed
code, talking to a desktop on this build:

- **Mobile ↔ desktop sessions and control are end-to-end encrypted and
  mutually authenticated over LAN and over the relay.** The relay sees the
  account uid and Firebase token used for *its own* authentication (which
  confer no desktop authority), the desktop id, tunnel setup messages, frame
  sizes and timing, and presence. It cannot read a request, a keystroke, a
  terminal frame, a file, or a permission decision, and it cannot act as the
  phone.
- A LAN attacker sees ciphertext and the plaintext `/v1/status` (which
  carries no secret). The paired device secret is never on the wire.

Still visible to the relay/cloud operator, unchanged by this work:

- the Firestore task index (title, prompt snippet, waiting snippet, attention
  reason, repo name/URL, branch, PR URL) — Slice 3;
- push notification title/body at the relay, FCM and APNs — Slice 4;
- desktop↔desktop relay KSP and `invoke` content, and the relay-attested
  bootstrap of the LAN TLS CA and the transfer key — Slice 5;
- routing metadata, timing, volumes and account identity at the relay —
  never claimable.

**Legacy window.** The desktop setting `mobile_legacy_access` (Preferences →
Mobile → "Allow legacy (unencrypted) mobile connections", default *on*)
keeps the pre-E2EE paths alive: plaintext pairing claims, bearer-secret LAN
requests and streams, plaintext relay tunnels and account-only relay
`invoke`s. **While it is on, an older phone (or anyone holding the relay's
account session) still reaches this desktop with the old authority, so the
deployment cannot be called protected** — this is an explicit migration
limitation, not a protected state. Turning it off refuses every one of those
paths; only sealed sessions remain. The desktop's Mobile preferences list
each paired device as end-to-end encrypted or not, and
`TrustedDevice.mobile_build` shows when each phone is on a runtime that pairs
sealed. Nothing in the desktop or mobile UI claims E2EE for a legacy pairing.

## 7. Failure and skew behaviour (what the phone shows)

| Situation | Phone | Wire |
|---|---|---|
| New phone, new desktop, sealed pairing | "End-to-end encrypted" | ciphertext only |
| Pinned key, desktop does not answer the handshake (old desktop, or a stripped handshake) | "Connection not verified — the desktop needs a newer Kanna"; no retry | one handshake frame, no plaintext KSP frame ever |
| Pinned key, wrong responder (rotated key, impostor) | "Desktop identity changed — remove and pair again" | as above |
| Handshake unanswered for 10 s | "Connection not verified — the desktop did not answer" | as above |
| Tampered/replayed/reordered frame after the handshake | "Connection interrupted"; session ends | nothing after the failure is delivered on either side |
| Legacy pairing (no pinned key) | "Not end-to-end encrypted — re-pair to upgrade"; works while the desktop allows legacy access | plaintext, as before |
| Old phone, new desktop, legacy on | works as before | plaintext |
| Old phone, new desktop, legacy off | refused with `legacy_access_refused` / 401 / 403 | plaintext refusal |
| Phone's secure identity unavailable (no keystore, no CSPRNG) | pinned desktops are "unavailable", never downgraded to legacy | nothing |

A refusal close (code 4910) is terminal for the `StreamClient`: it stops and
reports; it never falls back to a plaintext socket.

## 8. Native and release implications

- Mobile requires a new native binary: `expo-crypto` and `expo-secure-store`
  are native modules; `runtimeVersion` is bumped to `2.3.0` in every
  environment and the release version to 1.1.0. No OTA can deliver this to
  iOS 1.0.4 (5). The signed iOS 1.0.4 (5) / macOS .21 artifacts are untouched
  by this task.
- Desktop/server ship first through the normal staging RC train with legacy
  access on; the owner flips it off once paired phones report the new runtime.
- The relay needs no change: it never parsed tunnel frames and still does not.
