## 1. kojo

[jemdiggity/kojo](https://github.com/jemdiggity/kojo) is the user's own benchmark harness: it runs coding agents (Codex CLI, Claude Code) through SlopCodeBench's multi-checkpoint problems and grades every stage's code. Its **factory language** (`configs/factories/*.factory`, `src/kojo/factory_spec.py`, 353 lines; the runner `src/kojo/factory.py`, 648 lines; `docs/factory-language.md`) is the closest thing to what Kanna needs, and the sweeps it was built for (`fx-01` to `fx-06`, 30 factories) are the only runs of such pipelines on hand.

**Licence.** kojo has no `LICENSE` file yet; its 109 commits are all the user's, and the user has decided on MIT (2026-11-01), as kmux. The first build task adds it to kojo before porting the parser and validator, and records the provenance in `NOTICE`. This task copied no code.

### The language

```
build  = luna6:low
review = sol61:low prompt review-repro
verify = check repro
fix    = luna6:low

build -> review -> verify
verify -[fail, max 2]-> fix -> review
verify -[pass]-> done
```

- **Stages** are `NAME = [KIND] MODEL[:EFFORT] [xN] [by CHECKER] [guard CHECKER] [prompt NAME]`, or `NAME = check CHECKER [ARG]` for a deterministic stage with no model. The kind defaults to the stage's name (`review = opus55` is a review), and the kind picks the role prompt (`configs/factory-prompts/KIND.md`) and what the stage may touch: `build`, `revise`, `refactor`, `fix` change code and carry it forward; `review`, `qa`, `plan` read a disposable copy and their answer carries forward; `tester` writes a test suite from the specs and never sees code; `branch` builds independently and is kept aside for `check diff`.
- **Flows** are arrows: `a -> b -> c`, with options `-[fail]->`, `-[pass]->`, `-[max N]->`, `-[reset]->` (restart the destination from the checkpoint's starting code, with no feedback: a reroll) and `-[progress]->` (take the loop only while the check's failures differ from last time). From a stage, the first arrow in file order whose condition holds and whose `max` isn't spent is taken; nothing eligible ends the flow with the current code.
- **Verdicts.** `review` and `qa` end their answer with `VERDICT: PASS` or `VERDICT: FAIL` (the harness appends the request; a missing line is a fail); a `check` gives the same from its checker. Only verdict stages may have `pass`/`fail` arrows.
- **Feedback.** A verdict stage's answer (or a check's log, failures first, capped near 6000 characters) is appended to the next code-changing stage's prompt under a heading; a `plan`'s answer is appended to every later `build` of the checkpoint. Every stage runs in a **fresh conversation**.
- **Attributes.** `xN by CHECKER`: N independent attempts from the same code, the best score kept (best-of-n). `guard CHECKER`: score before and after; a stage that lowers the score is rolled back (`guard safe` is stricter: rolled back if the program no longer starts, the suite score fell, or more cases newly fail than newly pass).
- **Validation** (`validate()`): every stage reachable, every loop has a `max` on some arrow (so a factory always terminates), `pass`/`fail` only from verdict stages, a `fix` only after a verdict stage, no check before code exists, `suite` checks need a `tester`. Errors name the file and line. `max_sessions()` walks every verdict sequence for the worst-case session count, which the manifest records.
- **Checkers** are Python functions (`checks.py`): `smoke`, `examples`, `suite`, `safe`, `changed` (a bail-out detector: the build left the code byte-identical), `repro` (re-runs the reviewer's reproduction cases and forwards only confirmed failures), `diff NAME` (fuzz two builds against each other).

### The runner

`run_flow()` is one loop: pick the stage, run it (a model session, a check, N attempts, a guard), compute the verdict, pick the next arrow, record a trace row (`flow-trace.json`: stage, visit, verdict, next, scores, attempts and winner, guard before/after/rollback, `stalled`, `timed_out`). A timed-out fix is abandoned and its starting code carries on; after the flow, a final smoke check falls back to the newest code that starts. Every code-changing session's output is frozen read-only, graded and statically analysed (erosion, verbosity) afterwards; `run.json` per session keeps elapsed seconds, token usage by class, and the CLI's cost.

### What kojo is good at, and what it lacks

| Good at | Lacks (for Kanna) |
|---|---|
| A flow fits in ten lines and reads as a diagram | Static: a factory can't change while it runs; no fan-out besides `xN` |
| Loops always bounded; worst-case cost known before a run | Stages are fixed kinds for one benchmark shape (a CLI program graded by a suite) |
| Verdict stages, feedback forwarding, fresh conversations per stage | No user in the loop: no gate, no steering, no watching a stage work |
| `progress` and `changed` catch loops that spin | Headless `claude -p` / Codex exec: no visible pane, no resume, no messages |
| Guards and best-of-n as one-word attributes | Commands only as fixed checkers, not any shell command |
| A trace per visit; tokens and cost per session; grading of every stage output | State in JSON files per run, read by scripts; no live view |

## 2. Prior art: workflow languages and engines

Surveyed (sources in [§5](#5-sources)): GitHub Actions, Argo and Tekton, Temporal, Dagger, Prefect and Dagster, AWS Step Functions, Nextflow and Snakemake, LangGraph, CrewAI Flows, Mastra, the OpenAI Agents SDK, AutoGen GraphFlow, Semantic Kernel's process framework, Google ADK, Inngest, Trigger.dev and Restate, Claude Code's subagents, hooks and Workflow tool, Anthropic's workflow patterns, and the coding-agent factories (Factory.ai, Devin, OpenHands, SWE-agent, Codex cloud, Jules, Cursor cloud agents, the Ralph Wiggum loop, Aider's architect mode, CodeRabbit, Greptile, Spec Kit, Kiro, gh-aw).

**Every mature engine ends up with the same constructs:** a stage with inputs and outputs; explicit dependencies; fan-out over a run-time list with a concurrency cap and a fan-in (Actions' `matrix`, Argo's `withParam`, Step Functions' `Map`, LangGraph's `Send`); conditions on an upstream outcome; a bounded loop with an exit signal (ADK's `LoopAgent(max_iterations)`, Mastra's `dountil`, Spec Kit's converge, the Ralph plugin's `--max-iterations`); retry; a suspend or gate that waits for a token with a timeout (Argo `suspend`, Step Functions' task token, Temporal signals, LangGraph `interrupt`); budgets in time, turns and tokens (gh-aw, Claude's Workflow tool); memoised stage results so a relaunch replays what finished; isolation per stage (container, VM, worktree); and per-stage observability.

**How "the pipeline changes while it runs" is handled**, by family:

| Family | Examples | Dynamism | Cost |
|---|---|---|---|
| Declarative static DAG | Actions, Tekton, Step Functions, Snakemake | only instance counts (a matrix from a previous job's JSON) | predictable, poor at open-ended work |
| Code as workflow, replayed | Temporal, Inngest, Restate, Prefect, Claude's Workflow tool | the code decides each next step; a journal makes it resumable | determinism rules (the Workflow tool makes `Date.now()` throw), history growth |
| Graph with data-driven edges | LangGraph, Dagster `DynamicOut`, Nextflow, Argo recursion | node kinds fixed; instances and cycles decided by data | the usual middle ground |
| LLM as orchestrator | orchestrator-workers, handoffs, subagents, Ralph | the plan lives in a context window | least repeatable; gh-aw and Spec Kit wrap it in budgets and human gates |

Google's ADK deprecating its Sequential/Parallel/Loop templates for "graph-based and dynamic workflows" is a sign the field is settling on the middle rows.

**Worth copying for a tiny text format on a daemon with SQLite:** gates as stages, not chat (the Workflow tool forbids mid-run input and says to split at sign-off points); an append-only event table per run plus memoised stage results (OpenHands' event stream, Temporal's history); agent stages that emit declared, named JSON so shell and agent stages compose (the Workflow tool's `schema`, CodeRabbit's `custom_checks`); per-stage status, duration, tokens and turns with `logs` and `audit` commands (gh-aw); a warning on projected cost. **Worth avoiding:** unbounded loops (the original Ralph), silent caps, and writes outside a declared allowlist.

## 3. Evidence: which stages improve agent-written code

About 140 sources were read (papers, vendor engineering posts, field studies; the list in [§5](#5-sources) keeps the ones cited here). Ranked by strength of evidence:

| # | Stage or check | Effect | Caveat |
|---|---|---|---|
| 1 | **Run real tests in the fix loop** | Removing testing costs 12 to 39 points on HumanEval in LCG's ablation; removing review costs at most 2.4. Self-Debugging: +5 to 12 points with unit-test feedback, nothing from "reflection" alone. MapCoder: dropping the debugger hurts more than dropping the planner. | Function-level benchmarks; the signal is execution, not self-review. |
| 2 | **A failing reproduction test, used to filter or rerank** | Agentless 25.7% → 32.0% SWE-bench Lite with reproduction tests; SWE-RL 38.8 → 41.0; a repro filter lifts patch precision from 24% to 48% (SWT-bench) and 61% to 92% (Otter). | Filters discard many correct patches. "Reproduce first" is universal practice but never isolated in an ablation. |
| 3 | **A test writer separate from the coder** | AgentCoder: 71.3 → 79.9% HumanEval with a separate test designer; test accuracy 61 → 88%. Reflexion's self-written tests had 16% false positives and made results worse. | One direct ablation, GPT-3.5 era. |
| 4 | **Best-of-n at build, with a regression filter and a scorer** | Claude Opus 4 72.5 → 79.4% SWE-bench Verified; Trae 61.3 → 66.4 at n=3; five cheap samples beat one expensive one per dollar. | Cost about linear in n; verifiers close only 25 to 50% of the gap to an oracle. Without a verifier, selection plateaus. |
| 5 | **Spec clarity before building** | 38% of SWE-bench issues were underspecified; ambiguous prompts halve pass@1; ClarifyGPT 71 → 81% with real users. | Models rarely ask (about 0.3 questions per task). Kiro and Spec Kit publish no controlled evidence. |
| 6 | **A hard CI gate on agent PRs** | Each failed check cuts merge odds about 15%; CI failure is the top reason agent fix-PRs die; Meta's funnel (75% build, 57% pass, 25% add coverage) is what makes 73% of its generated tests accepted. | Observational. |
| 7 | **An external, trained critic** (not self-critique) | SWE-PRM 40.0 → 50.6% Verified; Nebius' trained critic doubles best-of-5, a prompted GPT-4o judge gave nothing. | Needs training data. |
| 8 | **Fresh context per stage, with an explicit hand-off** | SWE-agent: last 5 observations 18.0% vs full history 15.0%; restart with the diff carried over 66.6 → 71.8%, cold restart +0.2; a fresh-session review finds more than a repeated same-session one (F1 28.6 vs 21.7). | The hand-off needs an artifact (diff, plan, report); implicit decisions are lost otherwise. |
| 9 | **A different model reviews** | One same-model plus one cross-model review finds 57% of planted bugs vs 43% for two same-model; a model judging its own fresh patch loses 0.1 AUROC and approves injected patches 5× more. | Small planted-bug studies. |
| 10 | **Precision-gated review comments** | Uber uReview 75% useful; Meta lands low-risk diffs without human review at a 1 in 3 revert rate; unfiltered review gets 7 to 8% comment acceptance and slows PRs 42%. | Vendor telemetry. |
| 11 | **Security scan on known-weak classes** | 45% of LLM samples insecure, XSS fails 86%; no study isolates a scan stage in an agent pipeline. | |
| 12 | **Diff coverage, duplication, complexity** | 65% of agent PRs have no changed line executed by a test; Cursor adoption: warnings +30%, complexity +41%; GitClear: copy-paste 8 → 12%. | No study ties patch coverage to defects; Google uses coverage and mutants as review signals, not gates. |
| 13 | **A written plan first** | +8 to 13% for small models, +1 to 3% for frontier ones; +15 to 30% on hard problems, nothing on easy ones; plan-on-failure keeps most of the value at a fraction of the tokens. | Naive chain-of-thought hurts frontier models on easy tasks. |
| 14 | **Free-form LLM review** | ChatDev +7 points executability but completeness falls; LCG at most 2.4 points. | The value of "review" comes almost entirely from execution. |

**Against a stage:** self-review without execution is zero or negative (GPT-4 on GSM8K 95.5 → 89.0 after two self-correction rounds; Self-Refine on code -1.2); self-repair rarely beats more independent samples at equal budget; LLM-as-judge without execution is near chance on wrong code until it gets an interpreter; two-round review raises false positives (precision 0.30 → 0.20); heavy role-play frameworks cost 20 to 40× the tokens for gains a well-prompted single model mostly matches; LLM-generated tests are a weak verifier (62% of decisive repair tests fail on the gold patch); agents edit tests they can write to (GPT-5 special-cases tests on 54 to 76% of ImpossibleBench tasks, cut to 9% by an abort option); showing AI findings to reviewers rather than authors slows reviews.

**Loops and caps:** gains land in the first fix round and plateau after two or three (Self-Refine 22.0 → 27.0 → 27.9 → 28.8); failed trajectories run 30 to 80% longer; restarting with the diff beats continuing. **Field context:** agent PRs merge at about 65% vs 85% for humans; DORA 2024 and 2025 both find throughput up and stability down with AI adoption; METR's 2025 RCT found experienced developers 19% slower, its 2026 rerun 18% faster with wide intervals.

**Metrics with validity evidence:** pass@k and pass^k; resolved rate needs flakiness and hackability caveats (11% of SWE-bench Lite flaky, 28% of Verified accepts a wrong patch); cost per resolved issue; change failure rate (DORA); bug-inducing commit attribution (SZZ) tops out at F1 0.61, so defect-escape per run carries about a third noise; patch coverage and mutation score validated as review-time signals.

## 4. What Kanna takes, and what it leaves

| Takes | From | Leaves | Why |
|---|---|---|---|
| The whole flow syntax: `NAME = …`, arrows, `[pass]`, `[fail]`, `[max N]`, `[reset]`, `[progress]`, `done`, first-matching-arrow, every loop bounded, worst case computed, errors with file and line | kojo | kojo's fixed kinds and benchmark checkers | Kanna's stages are any agent, any command, a question, a merge |
| Verdict stages ending `VERDICT: PASS\|FAIL`; feedback appended under a heading; a fresh conversation per stage | kojo; evidence #8 | continuing one conversation through review and fix | fresh context with an explicit artifact beats a long one |
| `guard STAGE` and `xN by STAGE` as attributes | kojo; evidence #4 | best-of-n as the default | cost about linear in n; a first pipeline runs n=1 |
| Tests the agent can't edit as the gate (`run`), a reproduction test first (`bugfix.pipe`), a reviewer of another model | evidence #1, #2, #9 | review by the author's own session | self-review without execution measures nothing |
| Fan-out over a stage's named JSON output (`each`), the join a stage of its own | Workflow tool `pipeline`, Argo `withParam`, Dagster `DynamicOut` | instance counts fixed in the file | the plan knows the parts |
| Gates as stages that wait (`ask`), answered from the Desk or the CLI | Argo `suspend`, Step Functions' token, the Workflow tool's rule against mid-run input | a question in the agent's chat | the daemon drives, and the answer is recorded as an intervention |
| A run's pipeline can change: a stage declared `emits` adds stages and arrows as a new, validated revision, and so can the user | the user's requirement; Temporal child workflows, orchestrator-workers | a run that rewrites its own file freely | every revision is validated, bounded by the budget, kept and shown |
| Budgets in sessions and time; a trace row per visit; tokens, turns and cost per stage; an append-only event table | gh-aw, the Workflow tool, kojo's trace, OpenHands | metrics in files | they're queried: the Stats tab compares pipelines |
| Caps of 2 to 3 fix rounds, `progress` to stop a spinning loop, reroll (`reset`) over continuing | evidence (loops), kojo | unbounded retry | returns go negative after two or three |
| SZZ bugs-traced-back and changed-line coverage as quality columns, with their noise stated | the Code quality metrics task; evidence (metrics) | test count and pass rate as quality | all tests must pass anyway |
