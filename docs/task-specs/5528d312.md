# Task 5528d312 — automatic E2EE peer trust for signed-in same-account desktops

Plan recorded at the manual `plan` gate on 2026-09-18 and approved by the owner
with two additions (dev documentation in this repo, and a privacy-policy
follow-up in the separate kanna web repo). This file is the committed copy of
the plan the build stage executes; the same text is the plan stage's recorded
run result.

Owner directive (verbatim): "this is poor design then. it wasn't clear to me
that ee2e would require a ceremony. we should be able to have ee2e without a
ceremony if the user is signed in. whatsapp or similar products don't require
it."

## 1. Objective

Make two desktops signed into the same account pin each other's peer channel
keys automatically, so the sealed `kanna-ksc-peer` route works on first contact
with no `KANNA-PEER:` ceremony. The ceremony stays as the *verification* path
(upgrading an automatic pin to a verified one) and as the only path for
signed-out or cross-account machines. The sealed handshake, the sealed-only
routing rule ("a pinned peer never falls back to plaintext"), and the
loopback-authority doctrine are untouched: this changes how a `PeerDesktop`
record is *born*, not how a session is sealed or authorized.

Verified against the code: the only writer of `peer-desktops.json` today is the
ceremony (`peers.rs::pair_with_string` / `claim_pairing_offer`);
`peer_channel::dial_peer` returns `PairingRequired` on a missing record and
both the `/v1/peers/{id}/ksp` proxy and `invoke_desktop` surface it;
`admit_sealed_peer_session` (ksp.rs) grants an unknown key *pairing-only*
authority, which is exactly the authority an automatic enrollment claim needs.
The relay already binds a desktop socket to an account and a desktop id only
when that socket proved the desktop secret (`verifiedDesktopIdentities` in
`services/relay/src/router.ts`), and `list_active_desktops` is already served
from that registry. No private key leaves any machine in this design; only the
X25519 *public* key already in `peer-channel-identity.json` is announced. No
separate symmetric key exchange is needed: the Noise IK handshake derives fresh
symmetric session keys from the two pinned static keys plus ephemerals, with
forward secrecy.

### Terminology: the desktop-secret relay socket

`kanna-server` keeps one persistent outbound WebSocket to the relay. It is the
"desktop-secret relay socket" when it authenticates with
`{desktop_id, desktop_secret}` (`relay_client.rs::build_auth_message`) rather
than the older account-only `device_token`. "Desktop-secret" names the
*authentication* on that socket, not its encryption: the transport is TLS
(`wss://`) like every relay socket, TLS terminates at the relay, and the relay
reads every control frame on it. End-to-end encryption is a separate layer that
exists only inside sealed sessions riding through tunnels the relay opens.

The secret's life cycle: the desktop app mints it at sign-in and writes it into
`server.toml` (`apps/desktop/src-tauri/src/commands/mobile/config.rs`); the
renderer publishes its SHA-256 hash under the signed-in uid in Firestore
`desktopCredentials/{desktopId}` (`desktopCloudAssociation.ts`); the relay
verifies the presented secret against that hash
(`auth.ts::verifyDesktopCredentials`) and only then records the socket's
desktop identity as verified. Presence, sibling invokes and peer tunnels all key
off that mark. A second socket of the same kind with `tunnel_client: true`
opens each peer tunnel. The device token answers only "some member of this
account"; the desktop secret answers "which desktop of this account".

## 2. Trust model (the honest statement the docs must carry)

**Today:** a pin comes only from a string a person carried between screens, so
a compromised relay or account cannot MITM a pinned peer, ever.

**After:** at *first contact* the relay is the introducer. A relay that lies
about desktop B's key to desktop A (and vice versa) can insert itself once, at
enrollment. That is the WhatsApp/Signal trade and it is accepted, with these
mitigations, each of which is a concrete step below:

- **Trust on first use, then a real pin.** An automatic record is a full
  `PeerDesktop` pin. After it exists, every handshake is against that pin; a
  different key hard-fails with `peer_identity_mismatch` (existing behavior)
  and enrollment is *never* attempted while any record for that desktop id
  exists. The responder likewise refuses an enrollment claim for a desktop id
  it already pins under a different key. Nothing ever silently re-trusts.
- **Loud key change.** A mismatch is recorded on the peer record, surfaced in
  Preferences → Machines and the machine list as "identity changed", with the
  resolution spelled out: verify with a pairing string, or unpair and let it
  re-enroll.
- **Provenance is visible.** Every record says whether it was `verified`
  (ceremony) or `account` (automatic), in the peer list, the machine list and
  the panel badge; nothing labels an account pin as verified.
- **Optional out-of-band verification.** The existing ceremony run against an
  account-pinned peer replaces the record with provenance `verified` (the claim
  path already replaces the record; the change is the provenance field).
- **Introducer requires live proof, not a document.** The relay only lists a
  key for a socket that proved that desktop's secret *right now*; it persists
  nothing. A Firestore document was rejected because it would let a one-time
  account or rules compromise plant a key that survives indefinitely.
- **The ceremony refusal set still applies**: environment must match, the
  claimed id must equal the handshake hello's `sourceDesktopId`, a key held by
  another desktop id is refused, relay-origin sessions stay gated by
  `relay_tunnel_access_allowed`.

Still not protected (unchanged): metadata at the relay, and the legacy paths
while `desktop_peer_legacy_access` is on.

## 3. Distribution channel: relay presence registry (chosen)

The desktop's primary desktop-secret relay socket announces its peer channel
public key; the relay keeps it in memory beside the verified identity and hands
it out with presence. Each side verifies the *other's* key against that
registry, so it works over LAN and relay alike and an unauthenticated LAN
dialer cannot self-enroll.

Alternatives rejected:

- **Firestore `desktopCredentials` field.** The owner asked whether signed-in
  machines could simply publish a public key in Firestore. They could, and the
  trust model would be identical (TOFU with the cloud as introducer); only the
  key source differs. It was not chosen because the field is persistent and
  rewritable (a key planted once stays until noticed), the server has no
  Firestore client so the renderer would re-enter the sibling trust path the
  spec deliberately removed it from, spec §10 already promises keys are never
  read from Firestore, and it would need a Firestore rules change. Its one
  advantage, pinning an offline sibling, does not help opening a session,
  which needs the sibling online anyway. If it is ever wanted, the variant is:
  the renderer publishes `peerChannelPublicKey` beside `desktopSecretHash`,
  the relay returns it through the same `list_active_desktops` reply via the
  admin SDK with its credential cache invalidated on write, and steps 3
  onward below are unchanged.
- **Automatic ceremony over the legacy relay-attested `invoke`.** It dies with
  the legacy switch (`dispatch_relay_http_invoke` refuses it when off) and
  carries the request body through the relay in the clear.
- **Relay-side key binding in `tunnel_establish`.** The relay never sees a
  handshake static, so it cannot bind a key to a tunnel; the registry does
  that binding at auth time instead.

The announced key travels as a plaintext field on the TLS relay socket. That is
fine: the value is public and the relay is deliberately the introducer at first
contact. What the desktop secret adds is that the relay attaches the key only to
a desktop id whose socket proved the matching secret.

Capability discovery: no `desktopRouting` version bump. An old relay ignores
the new auth field and omits the new response field; the server treats the
absence as "enrollment unavailable" and behaves exactly as today. Old desktops
on a new relay announce nothing and are listed without a key, which is reported
as "runs an older Kanna".

## 4. Approach (steps in build order)

**Step 1 — relay (staging first).** `services/relay/src/index.ts` auth
handler: accept an optional `peer_channel_public_key` on the desktop-secret
(`msg.desktop_id && msg.desktop_secret`, non-tunnel-client) branch only;
validate it is a 43-char unpadded base64url string; pass it to
`setServerConnection`. `router.ts`: add
`announcedPeerChannelKeys: WeakMap<WebSocket, string>` set only when
`serverAuthProof.kind === "desktop"` and ids match (mirror
`verifiedDesktopIdentities`). Extend the `list_active_desktops` reply with
`desktops: [{ desktopId, peerChannelPublicKey: string | null }]` next to the
unchanged `desktopIds`. Tests in a new
`services/relay/src/peerKeyAnnouncement.test.ts` (same style as
`desktopTunnel.test.ts`): key listed for a desktop-secret socket; ignored for
device-token and tunnel-client sockets; malformed key refused; `desktopIds`
unchanged. Deploy with `./kd cloud deploy` to staging only.

**Step 2 — server announces and reads keys.**
`relay_client.rs::build_auth_message`: add
`peer_channel_public_key: Option<String>` to `RelayMessage::Auth`, populated
from `state.peer_channel_identity()` only on the desktop-secret, non-tunnel
branch (`relay.rs` passes the identity in; a failed identity announces
nothing). `http_api/state.rs`: change `DesktopRelayRequest::ListActive` to
resolve `Vec<RelayDesktopPresence { desktop_id, peer_channel_public_key:
Option<String> }>` plus a `bool` "relay supports key presence"; keep
`list_active_relay_desktops()` returning ids as a wrapper and add
`list_active_relay_desktop_presence()`. `relay.rs::resolve_pending_desktop_request`
parses `desktops` when present, else synthesizes from `desktopIds` with `None`
keys.

**Step 3 — provenance and mismatch on the record.** `peer_trust.rs`: add
`PeerProvenance { Verified, Account }` with `#[serde(default)]` = `Verified`
(every pre-existing record came from the ceremony, so migration is the
default), `identity_mismatch_at_unix_ms: Option<u64>`, methods
`record_identity_mismatch`, `clear_identity_mismatch`, `provenance`. Store
version stays 1. `upsert` semantics unchanged (ceremony still replaces; that is
the upgrade path).

**Step 4 — the enrollment claim route.** New
`crates/kanna-server/src/peer_enrollment.rs` with the claim types
(`PeerAccountEnrollClaim { desktop_id, desktop_name, environment,
transfer_identity }`, response reusing `PeerPairingClaimResponse`) and the
verification function. New handler `peers.rs::claim_account_enrollment` at
`POST /v1/peers/account-enroll`, reachable only with
`SealedPeerPairingContext` (register it in `router.rs` exactly like
`/v1/peers/pairing/claim`, and add its row to `docs/task-specs/c9f5721b.md`).
Checks in order: context present; `desktop_id_is_pairable`;
`declared_desktop_id == claim.desktop_id`; not self;
`environment == config.environment`; `authenticated_account_uid()` is `Some`;
`list_active_relay_desktop_presence()` lists `claim.desktop_id` with a key
equal to `context.encoded_remote_static()` (else 403
`peer_enrollment_refused`); existing record for that id with a different key →
409 `peer_identity_mismatch`, record `identity_mismatch_at`, publish `Settings`
state change, nothing replaced; same key → touch only; otherwise persist
`PeerDesktop { provenance: Account, account_uid: Some(uid), .. }`, close the
pooled session, sync transfer proxies, reply with this desktop's transfer
identity. This is the one place an automatic pin is written on the responder.

**Step 5 — the initiator.** `peer_enrollment::try_enroll(state, desktop_id)
-> Result<PeerDesktop, PeerEnrollError>`: refuse fast when signed out,
`!desktop_routing_available()`, or already pinned; look the sibling up in relay
presence (`Offline`, `NoKey` = older Kanna, `RelayTooOld`); guard one in-flight
attempt per target and a 30 s negative cache (same shape as
`begin/finish_lan_bootstrap_attempt`); `dial_peer_with_key(.., PeerHello::Pairing)`
against the announced key (reusing the pairing intent keeps
`kanna-secure-channel` untouched and gets pairing-only authority on the far
side); `auth`, then the claim; on 200 verify `desktop_id`/`environment` in the
reply and persist `provenance: Account`, `account_uid: Some(uid)`; on 409 map
to `SiblingHoldsDifferentPin`. Handshake success against the relay-announced
key plus `responder_hello.desktop_id == desktop_id` is what proves the far side
holds that key.

**Step 6 — trigger points, making `peer_pairing_required` unreachable for the
signed-in case.** `peer_channel::dial_peer`: on `Ok(None)` call `try_enroll`
and continue with the fresh pin; on failure return `PairingRequired(reason)`
(extend the variant with a detail string so the message says *why*: "not
signed in", "that machine is offline", "that machine runs an older Kanna",
"the relay does not support automatic pairing yet", "that machine holds a
different key for this desktop"). Code stays `peer_pairing_required`. Covers
the `/v1/peers/{id}/ksp` renderer proxy and `PeerSessions` unchanged.
`invoke_desktop::invoke_desktop`: in the `Ok(None)` branch call `try_enroll`
before the legacy fallback; enrolled → `invoke_peer`; otherwise existing
legacy/error behavior with the reason appended. On `IdentityMismatch` in
`dial_peer`, call `record_identity_mismatch` and publish `Settings`; clear it
on the next successful handshake. `cloud_desktops::list_cloud_desktops`: for
each active relay desktop with a key and no record, spawn `try_enroll` in the
background (deduped by the guard) so both directions are pinned from one
exchange and the list shows `e2ee` on its next refresh without anyone opening
a session.

**Step 7 — surfaces.** `peers.rs::PeerView` and
`cloud_desktops::MachineDescriptor`: add `provenance: "verified" | "account"`
and `identityChanged: bool`; `encryption` values are unchanged for
CLI/MCP/mobile compatibility (no consumer outside `desktopServerClient.ts`
reads it). Desktop: `desktopServerClient.ts` types; `MachinesPanel.vue` badge
text "End-to-end encrypted · verified" vs "End-to-end encrypted ·
account-trusted" with a one-line hint ("Pinned automatically because both Macs
are signed into your account. Verify with a pairing string to rule out a
compromised relay."), a red "Key changed" line with the two resolutions when
`identityChanged`, and the intro/`pairHint`/`legacyHint` copy reworded so the
ceremony reads as verification (en/ja/ko). No toast: the panel provenance is
the one-time non-blocking notice.

## 5. Environment, legacy switch, migration, sign-out

- Environment: staging and production use different relays; dev uses the
  harness relay. The claim carries `environment` and is refused on mismatch,
  and the store is environment-scoped, unchanged.
- Legacy switch: unchanged in this task, default on. With it on, an unpinned
  sibling now gets one enrollment attempt before the plaintext fallback; with
  it off, enrollment is the only way in and the reason text says why it could
  not happen.
- Migration: manually paired records deserialize as `verified`; nothing else
  changes on disk.
- Sign-out / account change: automatic records are always account-bound, so
  the existing `retain_account` purge drops them; they re-enroll on the next
  sign-in. A signed-out machine or one on another account is never listed by
  the relay, so `peer_pairing_required` remains its answer and the ceremony
  its path.

## 7. Risks, open decisions and follow-ups outside this repo

- Relay ordering: desktops on this build against the old staging relay simply
  keep today's behavior; the relay must be deployed to staging before the E2E
  is meaningful. Production is out of scope.
- Eager background enrollment from `list_cloud_desktops` can race with a lazy
  one from the other side; both write identical records and `upsert` is
  idempotent, but the build must keep the in-flight guard per target. The
  owner accepted keeping the eager trigger.
- `PairingRequired` grows a reason string; any client matching the message
  text rather than the code (none found) would change.
- Relay presence is per relay process; a relay restart clears the registry
  until desktops reconnect, which they already do.
- **Follow-up in the separate kanna web repo (owner-flagged): the published
  privacy policy must describe desktop-to-desktop trust after this ships**
  (same-account desktops introduced by the relay at first contact, pinned
  thereafter, verifiable by pairing string; the relay carries ciphertext plus
  metadata). This task cannot edit that repo; the §11 draft paragraph in
  `docs/specs/secure-channel.md` is the reviewed wording that follow-up
  copies, and `docs/legal/privacy-policy.md` here changes only when that
  policy is republished with new effective dates.
- Follow-up candidate: retire the legacy switch default after this ships on
  both machines.

## 8. Build recommendation

Strong tier. The work crosses four boundaries (relay TypeScript, server Rust
trust and routing, desktop UI, two-instance E2E) and its correctness is a
security property; a mechanical model will get the plumbing right and the
refusal ordering wrong. The pinned `in progress` stage names `claude-opus-med`
first; a fable-tier override on advance is warranted.
